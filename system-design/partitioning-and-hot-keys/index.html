Partitioning & Hot Keys

When one machine can no longer hold the data: shard keys, consistent hashing, resharding and the celebrity problem.

35 min 6 topics blueprint Scale
Mental modelPartitioning buys capacity by making a routing decision. A bad key concentrates traffic; a good key spreads it without making common queries impossible.

The shape

Read the diagram from the caller to the data. Each layer has one job; the interesting part is what crosses a boundary and what happens when it does not arrive.

Core ideas

  • Hash partitioning spreads writes evenly but makes range queries expensive.
  • Range partitioning keeps related rows together but risks uneven shards.
  • Consistent hashing reduces data movement when nodes join or leave.
  • A hot key is a distribution problem; replicate it, split it or cache it.
  • Resharding must be planned before the first shard fills up.

Decisions and their costs

There is no free architecture. Each row is a choice, the situation that makes it reasonable, and the bill that arrives later.

01

Hash the tenant or user id

Choose it when

Access is mostly by one user and even write distribution matters.

What it costs

Cross-user range queries need a secondary index or fan-out.

02

Range by time or region

Choose it when

Queries naturally scan a range and locality matters.

What it costs

Recent ranges become hot and need splitting.

03

Replicate a hot key

Choose it when

A single key receives disproportionate traffic.

What it costs

Writes to that key still need a single owner.
