Case study 01 \u00b7 Warm-up

Design a URL shortener

A small read-heavy system with a surprisingly sharp key-design problem.

25 min 4 requirements 4 layers 3 trade-offs
Design prompt15 min · say it out loud

Design a URL shortener for a product with 50 million redirects per day. Users can create a short link, choose an optional custom alias, see click counts, and deactivate a link.

Take it to the board

1. Requirements

Start with what the system must do, then separate it from how well it must do it. These are the functional promises this design keeps.

  • Create a short link from a long URL, with an optional custom alias.
  • Redirect a short code to its destination with low latency.
  • Track click counts without slowing the redirect path.
  • Allow the owner to deactivate a link immediately.

2. Constraints and assumptions

Every estimate below depends on these. If the interviewer changes one, the design should change with it.

  • Reads outnumber writes by roughly 1,000:1.
  • Redirects should resolve in under 100 ms at p95.
  • A short code should be unguessable when the user wants privacy.
  • Analytics may be a few minutes stale.

3. Back-of-the-envelope estimates

Redirect QPS~580 / s

50M per day, with a 2x peak allowance.

New links~12 / s

1M new links per day is a generous planning number.

Code space62^7 ≈ 3.5T

Base62 with seven characters is ample for this scale.

4. The shape

Read the diagram from the caller to the data. The interesting part is what crosses a boundary and what happens when it does not arrive.

5. API surface

A small, explicit contract. Each endpoint should say what it accepts, what it returns and whether repeating it is safe.

MethodPathPurpose
POST/linksCreate a short link and return its code.
GET/:codeResolve the code and return a 302 redirect.
GET/links/:codeRead metadata and click totals for the owner.
DELETE/links/:codeDeactivate a link immediately.

6. Data model

The data model is where most of the design hides. Name the key, the access pattern and what grows without bound.

Table / streamFields and notes
linkscode (PK), long_url, owner_id, custom_alias, created_at, revoked_at
clickscode, occurred_at, country, referrer, user_agent (partitioned by day)
idempotencyowner_id + request_key, response_json, expires_at

7. Generate the code, not the row

The central choice is how a short code is produced. A random Base62 code gives you an even distribution and makes enumeration hard. A sequential ID encoded in Base62 is easier to generate but leaks volume and is guessable.

For this product, random seven-character codes with a uniqueness check are a good default. Collisions are rare at this scale, and a retry loop handles them without coordination.

  • Random code: harder to enumerate, no central sequence, requires a collision check.
  • Sequential code: simple, but leaks creation order and needs an extra layer for privacy.
  • Custom alias: a separate unique index; reserve it before the generic code path.

8. Make the redirect boring

The redirect path should do one thing: look up a code and return a 302. Put a cache in front of the key-value store, keep the service stateless, and send click events to a durable stream instead of writing synchronously.

Deactivation needs to win over cached data. A short TTL plus a revocation event that deletes the cache entry keeps the window bounded. If immediate revocation is a hard promise, check a small revocation set on every redirect.

9. Analytics is a different product

Click counts are append-only events. Ingest them into a stream, aggregate in windows, and serve the owner a slightly stale total. Never put a counter update in the redirect transaction: a slow analytics store should not make links slow.

Bot filtering and deduplication belong in the analytics pipeline, not in the redirect. The redirect should remain fast even when the analytics pipeline is down.

Decisions and their costs

There is no free architecture. Each row is a choice, the situation that makes it reasonable, and the bill that arrives later.

01

Cache-aside the code mapping

Choose it when

Reads dominate and a few minutes of stale metadata is acceptable.

What it costs

Deactivation needs an invalidation path.

02

Async click events

Choose it when

Analytics can lag without breaking the core experience.

What it costs

You need a durable queue and an aggregation job.

03

Random Base62 codes

Choose it when

Privacy and unpredictability matter more than compact IDs.

What it costs

A collision check and retry path.

What breaks first

Failure is normal. The useful question is not whether a component fails, but what the user sees when it does.

FailureImpactMitigation
The cache is cold after a deployA burst of database reads raises redirect latency.Warm popular codes and add request coalescing per key.
Analytics stream is unavailableClick totals fall behind.Buffer locally, retry with backoff, and show freshness in the UI.
A custom alias collidesThe create request could overwrite an existing link.Use a unique constraint on alias and return 409.
