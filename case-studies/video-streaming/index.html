Case study 05 \u00b7 Intermediate

Design video streaming

Upload pipelines, transcoding queues, adaptive bitrate and a CDN that carries the load.

40 min 5 requirements 4 layers 3 trade-offs
Design prompt24 min · say it out loud

Design a video streaming platform for creators and viewers. Uploads should return quickly, videos should play on mobile and desktop, and the system should survive a viral video.

Take it to the board

1. Requirements

Start with what the system must do, then separate it from how well it must do it. These are the functional promises this design keeps.

  • Upload a source video and return immediately.
  • Produce multiple resolutions and formats.
  • Stream with adaptive bitrate.
  • Track view progress and resume playback.
  • Handle a single video receiving millions of views.

2. Constraints and assumptions

Every estimate below depends on these. If the interviewer changes one, the design should change with it.

  • Uploads can be gigabytes; the request must not hold a worker for the whole transfer.
  • Playback start should be under 2 seconds on a good connection.
  • Transcoding is CPU-heavy and can take minutes.
  • Most traffic should be served from the edge, not the origin.

3. Back-of-the-envelope estimates

Uploads~10k / day

Planning number for a mid-sized creator platform.

Views~50M / day

The CDN carries the majority of bytes.

Renditions4–6

240p to 4K, plus a thumbnail and manifest.

4. The shape

Read the diagram from the caller to the data. The interesting part is what crosses a boundary and what happens when it does not arrive.

5. API surface

A small, explicit contract. Each endpoint should say what it accepts, what it returns and whether repeating it is safe.

MethodPathPurpose
POST/videosCreate a video record and return a resumable upload URL.
GET/videos/:id/playbackReturn a signed manifest URL and playback metadata.
POST/videos/:id/progressSave playback position and completion state.
GET/videos/:id/statusPoll processing state for the creator.

6. Data model

The data model is where most of the design hides. Name the key, the access pattern and what grows without bound.

Table / streamFields and notes
videosvideo_id, creator_id, status, source_key, duration, created_at
renditionsvideo_id, resolution, codec, segment_prefix, ready_at
view_progressuser_id, video_id, position_seconds, updated_at

7. Upload directly, process asynchronously

The upload service should not proxy gigabytes through an application server. Issue a signed, resumable upload URL to object storage, then emit an event when the object is complete. The API returns a video id immediately and the UI polls or subscribes to status.

Transcoding is a queue of independent segment jobs. A single source is split into chunks, each chunk produces renditions, and a manifest is assembled when all parts are ready. This makes retries cheap and lets you scale workers horizontally.

8. Adaptive bitrate is a file layout problem

Streaming is not one large MP4. Produce segmented renditions and a manifest that lists them. The player chooses a rendition based on measured bandwidth and buffer health. Keep segment durations short enough to adapt, but not so short that request overhead dominates.

A viral video creates a hot object problem. The CDN absorbs the read traffic; origin should see a small fraction of requests. Pre-warm the manifest and first segments when a video is published, and set cache headers deliberately.

  • Segment size: a few seconds, aligned across renditions.
  • Manifest: signed, short-lived, cacheable at the edge.
  • Hot video: pre-warm popular segments and protect origin.

9. Playback state and failure

Playback progress is a low-value, high-volume write. Buffer it client-side and send it periodically. A lost progress update should never block playback. Use a per-user, per-video upsert and tolerate last-write-wins.

If transcoding fails, keep the source and the job state. Retry only the failed segments. If the manifest is missing, return a clear processing state instead of a broken player.

Decisions and their costs

There is no free architecture. Each row is a choice, the situation that makes it reasonable, and the bill that arrives later.

01

Direct-to-object-storage upload

Choose it when

Files are large and the API tier should stay stateless.

What it costs

You need signed URLs, CORS and completion events.

02

Segmented transcoding

Choose it when

Jobs are long and retries should not restart from zero.

What it costs

A manifest assembly step and more object storage operations.

03

CDN-first delivery

Choose it when

Read traffic is high and content is cacheable.

What it costs

Cache invalidation and signed URL policy become part of the design.

What breaks first

Failure is normal. The useful question is not whether a component fails, but what the user sees when it does.

FailureImpactMitigation
A transcoding worker diesA segment never completes and the video stays processing.Job leases, heartbeats and retry with a maximum attempt count.
A video goes viralOrigin and metadata reads spike.CDN caching, pre-warm, request coalescing and rate limits.
Playback progress writes failThe viewer loses resume position.Client buffer, retry later, and keep playback independent.
