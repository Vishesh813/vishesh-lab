Case study 02 \u00b7 Intermediate

Design real-time chat

WebSockets, fan-out, presence and the delivery guarantees behind a simple message bubble.

40 min 5 requirements 4 layers 3 trade-offs
Design prompt24 min · say it out loud

Design a chat product for 5 million daily users. It supports direct messages, groups up to 500 people, read receipts, presence, and offline delivery. Messages must not be lost.

Take it to the board

1. Requirements

Start with what the system must do, then separate it from how well it must do it. These are the functional promises this design keeps.

  • Send and receive messages in real time for direct and group conversations.
  • Persist message history and support pagination.
  • Show delivery and read state per participant.
  • Deliver messages to a user's other devices.
  • Catch up on messages after an offline period.

2. Constraints and assumptions

Every estimate below depends on these. If the interviewer changes one, the design should change with it.

  • Message send should feel instant; 300 ms server acknowledgement is a reasonable target.
  • Message history must be durable and ordered within a conversation.
  • Presence can be eventually consistent and can expire.
  • A user may have up to five active devices.

3. Back-of-the-envelope estimates

Active sockets~1M concurrent

20% of daily users online at peak.

Messages~700 / s

50M messages per day, 2x peak.

History~20 KB / user / day

A planning estimate, not a retention policy.

4. The shape

Read the diagram from the caller to the data. The interesting part is what crosses a boundary and what happens when it does not arrive.

5. API surface

A small, explicit contract. Each endpoint should say what it accepts, what it returns and whether repeating it is safe.

MethodPathPurpose
POST/conversations/:id/messagesPersist a message and enqueue fan-out.
GET/conversations/:id/messages?before=Page backwards through history.
POST/messages/:id/readRecord a read receipt for the current user.
WS/realtimeReceive new messages, typing and presence events.

6. Data model

The data model is where most of the design hides. Name the key, the access pattern and what grows without bound.

Table / streamFields and notes
messagesconversation_id (partition), message_id (sort), sender_id, body, created_at, client_nonce
conversation_membersconversation_id, user_id, joined_at, last_read_message_id
presenceuser_id, device_id, last_seen_at, ttl

7. Accept, persist, then fan out

A message send is a write, not a broadcast. Validate the sender's membership, assign a server-side message id, persist the message, then enqueue fan-out. The sender receives an acknowledgement with that id; the recipients receive the message through their sockets or a push notification.

The client-generated nonce is important. A mobile client may retry after a timeout; the server uses the nonce to make the write idempotent and returns the existing message instead of creating a duplicate.

8. Ordering is per conversation

Global ordering is unnecessary and expensive. Partition the message store by conversation id, use a sortable message id or sequence, and page backwards with a cursor. For groups, fan-out writes can be asynchronous, but the canonical message remains in the conversation partition.

Presence is a different consistency class. A heartbeat with a TTL is enough. Do not block a message send on presence, and do not show 'online' as a permanent fact.

  • Direct message: one conversation partition.
  • Group: one canonical message plus fan-out to members.
  • Offline: push notification plus a catch-up cursor on reconnect.

9. Offline catch-up and multiple devices

Each device tracks the last message id it has seen. On reconnect it asks for messages after that cursor, not for the whole conversation. A per-device cursor also makes read receipts honest: reading on a phone should not mark messages read on a laptop unless the product says so.

Sockets are expensive and mobile networks are unreliable. Keep connections at the edge, use heartbeats, and fall back to long polling or push when a socket cannot be established.

Decisions and their costs

There is no free architecture. Each row is a choice, the situation that makes it reasonable, and the bill that arrives later.

01

WebSocket gateway

Choose it when

You need low-latency bidirectional events and presence.

What it costs

Stateful connections, sticky routing and connection draining.

02

At-least-once fan-out

Choose it when

Duplicate suppression is cheaper than losing a message.

What it costs

Consumers need idempotency and clients need deduplication by message id.

03

Per-conversation ordering

Choose it when

Global order has no product meaning.

What it costs

Cross-conversation ordering is not defined; that is usually fine.

What breaks first

Failure is normal. The useful question is not whether a component fails, but what the user sees when it does.

FailureImpactMitigation
A socket gateway diesAll connected users on that node reconnect at once.Add jitter to reconnect backoff and keep gateway capacity headroom.
Fan-out lagsMessages are stored but not delivered in real time.Surface unread state, use push fallback, and monitor consumer lag.
Duplicate send after timeoutThe same message appears twice.Unique client nonce per conversation and idempotent writes.
